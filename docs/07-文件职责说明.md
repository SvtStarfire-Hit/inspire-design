## 7. 附：两条出口的运行原理（零基础可读）

> 不熟悉 npm / MCP 也能看懂：这一节说明「npm run web」与「mcp-server.js」到底是怎么跑起来的。

### 7.1 共同前提：它们都是 JavaScript 程序，靠 Node.js 运行

Node.js 是一个「能在电脑上直接运行 JavaScript」的程序。本项目的两个出口都是 JavaScript 写的，所以电脑上装了 Node.js、并执行过一次 `npm install`（装好所需依赖）后才能跑。

### 7.2 页面端：在你自己电脑上开一个「小网站」

`npm run web` 连起来做三件事：

1. npm 查 package.json 的 `scripts` 表，找到 `web` 一行——内容是 `node serve-web.js`
2. 于是实际动作是：让 Node.js 运行 serve-web.js 这个文件
3. serve-web.js 在你的电脑上开一个「服务窗口」（端口 4173），把项目文件夹按网址对外提供——浏览器请求 `http://localhost:4173/web/` 时，它按 URL 找到对应文件并返回（这就是「静态文件服务器」）

几个容易困惑的点：

- `localhost` 意思是「本机」：这个小网站只有你这台电脑能访问，不是发布到互联网上的站点
- 为什么不能直接双击 `web/index.html` 打开：浏览器的安全规则禁止 file:// 页面跨目录加载数据模块，而页面端要加载仓库里 `data/` 的同一份内容，所以必须借这个小服务器中转
- 停止：回到运行它的终端按 Ctrl+C；之后随时可再跑一次 `npm run web`

### 7.3 MCP 端：AI IDE「按需叫醒」的一个工具进程

先一句话解释 MCP（Model Context Protocol）：它是 AI IDE 与「外部工具」之间的一套通信约定。工具不必做成 IDE 插件，而是一个独立进程——IDE 负责启动它、和它来回传消息。

mcp-server.js 就是这样被使用的：

- **注册** ＝ 在 AI IDE 的 MCP 配置里留一条「启动命令」（`node .../mcp-server.js`），相当于给 IDE 留了张便签：「用到时，用这个命令叫我」
- **运行** ＝ IDE 需要时自己启动这个进程；随后 AI 与它通过「标准输入 / 标准输出」（进程的两根传声管）互发 JSON 消息：AI 要某阶段的约束包 → 进程把内容发回去
- **无端口、无网络、不常驻后台**：进程跟着 IDE 会话走，IDE 关闭即退出；下次打开 IDE 按便签重新叫醒
- **不需要你手动运行**：手动跑 `node mcp-server.js` 它只会静静地等消息——它的「嘴」（输出）是给 IDE 看的，不是给人看的

### 7.4 一张表记住两者

| | 页面端 | MCP 端 |
|---|---|---|
| 给谁用 | 你，在浏览器里看 | AI，在 IDE 对话中被调用 |
| 谁来启动 | 你手动 `npm run web` | AI IDE 按注册配置自动叫醒 |
| 活多久 | 到你按 Ctrl+C | 到 IDE 关闭 |
| 怎么通信 | 浏览器发 HTTP 请求，服务器回文件 | 与 IDE 用标准输入 / 输出互发 JSON 消息 |
| 涉及网络吗 | 仅本机（localhost:4173） | 完全不涉及 |
| 内容从哪来 | 服务器读仓库里的 web/ 与 data/ 文件 | 进程读同一份 data/ —— 这就是两边内容一致的原因 |

### 7.5 顺带搞懂：npm run / npx 是怎么回事

- `npm run xxx` 的机制：查 package.json 的 `scripts` 表，执行 xxx 对应的那行命令。本项目四条：`npm install`（装依赖，只需一次）、`npm start`（跑 MCP 端，日常不需要——由 AI IDE 代管）、`npm test`（自检）、`npm run web`（开页面端）
- 你可能见过的 `npx -y @some/mcp-server` 写法：npx 会「先从 npm 下载这个包，再执行」。本项目用的是 `node mcp-server.js` —— 文件就在仓库里，无需下载、改完立即生效
