## 2. 各改进项详细说明

### 2.1 一份稿子多状态（`?query` 模式）—— P0

**问题**：当同一界面有多种运行模式/状态（如"人工/辅助/全自动"三种模式），
按当前指导会做成三份 HTML，然后陷入"改一处要改三处，很快走样"的坑。

**Animals 的解法**：一份 HTML 通过 URL 查询参数（`?mode=assist|manual|auto`）切换状态，
`PAGES` 表支持带查询串的条目，一份稿子出多张交付图。

**改进动作**：
1. stages.js 阶段 4（main）的 `rules` 增加：
   "同一界面有多种运行模式/状态时，用 URL 查询参数切换，不要为每个状态另存一份 HTML"
2. stages.js 阶段 5（spec）的 `rules` 增加同样的条目
3. WPF-README.md §3.4 的 `PAGES` 表说明增加"一项可以带查询串"的模式与示例
4. WPF-README.md §8 坑清单增加对应条目

**Animals 实例**：
```python
# export-png.py PAGES 表
PAGES = [
    ("fig1-assist", "fig1-主界面总览.html?mode=assist", "01-辅助分拣.png", 1942, 1046, False),
    ("fig1-manual", "fig1-主界面总览.html?mode=manual", "02-人工分拣.png", 1942, 1046, False),
    ("fig1-auto",   "fig1-主界面总览.html?mode=auto",   "03-全自动分拣.png", 1942, 1046, False),
]
```

### 2.2 裁定记录机制 —— P0

**问题**：当前 `humanCheckpoint` 只说"等人说行"，没有指导"确认后把决定记在哪里、用什么格式"。
WPF-README.md §5.4 说了"把口头裁定写下来"，但没有给出模板。

**Animals 的解法**：在设计文档里维护"历次裁定"章节，按轮次记录每个决策的"原问题 → 结论"，
4 轮积累 10+ 条关键裁定，后续每一稿都遵守。

**改进动作**：
1. stages.js 阶段 0（blueprint）的 `deliverables` 增加"裁定记录"（初始为空）
2. stages.js 阶段 0 的 `rules` 增加：
   "每轮确认的决定必须写进语言版设计文档的'历次裁定'章节，后续每一稿必须遵守"
3. WPF-README.md §5.4 补充裁定记录的格式模板

**Animals 实例**：
```markdown
#### 第 2 轮（2026-09-10）
| # | 原问题 | 结论 |
|---|--------|------|
| 1 | `YYDD` 的含义 | 「月日」简写，作为可选的日期格式别名 |
| 2 | 分类树层级来源 | 由平台侧维护一张映射表，不从模型标签推导 |

#### 第 3 轮（2026-09-11）
| # | 原问题 | 结论 |
|---|--------|------|
| 1 | 辅助模式的标签条有「待人工确认」琥珀态 | 取消。不存在"必须人工确认"的图片 |
```

### 2.3 规格页三种类型 —— P1

**问题**：阶段 5 只说"一个文件 = 一组'面向部件'的规格"，没有区分规格稿的类型。
实践中容易只画"界面长什么样"，忘了画"数据怎么流转"和"算法怎么工作"。

**Animals 的解法**：4 张规格稿自然分成三类：
- 组件规格（fig2：卡片结构与标签状态）
- 流程规格（fig3：Mermaid 流程图 + 责任分工）
- 数据结构规格（fig4：分类树 / 映射表 / token 表）

**改进动作**：
1. stages.js 阶段 5（spec）的 `guidance` 增加规格稿三种类型提示
2. stages.js 阶段 5 的 `pitfalls` 增加"只画了界面规格，漏了流程和数据规格"

---

### 2.4 业务驱动的索引色板 —— P1

**问题**：阶段 2 的令牌指导只覆盖"颜色 / 圆角 / 间距 / 字号 / 尺寸基准"，
没有"索引色板"的概念。涉及分类/标签/类型区分的项目会漏掉。

**Animals 的解法**：`--cat-1` 到 `--cat-12` 的 12 色分类色板，通过 `Category.ColorKey` 索引，
用于树节点、标签条、日志的视觉一致性。

**改进动作**：
1. stages.js 阶段 2（tokens）的 `guidance` 增加索引色板指导
2. stages.js 阶段 2 的 `aiPromptTemplate` 的类别列表加上"分类色板（如有）"

---

### 2.5 语言版文档分层模板 —— P2

**问题**：WPF-README.md §5.5 只提了一种"语言版设计文档"。
Animals 实践表明至少需要区分"项目设计"（功能边界）和"设计方案"（视觉决策 + 裁定记录）两类。

**Animals 的四层文档**：
| 文档 | 职责 |
|------|------|
| 01-项目设计文档 | 是什么 / 给谁用 / 功能清单（阶段 0 产物） |
| 02-技术架构文档 | 怎么实现 / 分层 / 数据流 / ADR |
| 03-UI 说明文档 | 界面长什么样 / 控件规格 / 状态机 |
| 06-界面重设计方案 | 为什么这么设计 / 裁定记录 / 待确认项 |

**改进动作**：
1. stages.js 阶段 0 的 `guidance` 增加文档分层建议
2. WPF-README.md §5.5 补充分层模板

---

### 2.6 工具命名语义化 —— P2

**问题**：`render.py` 和 `measure.js` 的名字不够直白。

**Animals 的改法**：
- `render.py` → `export-png.py`（"出图"比"渲染"更直白）
- `measure.js` → `check-layout.js`（"体检布局"比"度量"更准确）

**改进动作**：
1. capabilities.js 里的 `file` 和 `usage` 字段更新
2. stages.js 里引用的工具名更新
3. WPF-README.md 和 docs 里的工具名更新

> 注意：实际脚本文件不改名（Animals 项目里是复制后改的名），
> 只改 InspireDesign 文档与数据中的引用名。
> 或者：同时把 InspireDesign 自身的脚本也改名，保持一致。
> **决定**：同时改名，保持 InspireDesign 自身与文档一致。
